# 第4回 解答：独自評価セットによるLLM採点器の検証

## 演習（講義配布の評価セット）

講義配布の10問を使う演習（STEP 1〜3）は、今回の実験とは別であり、配布セットに対する人手採点・講師ラベルとの比較・ルーブリック変更前後の再採点は実施していない。本提出では宿題の**「実装」**を選択し、独自に作問した10問で評価した。配布セットの演習結果を、独自セットの結果から推測して埋めることはしない。

## 宿題：実装

### 1. 目的と評価セットの設計

目的は、エージェントの正答率を測ることだけではなく、**LLM-as-a-Judgeが人手の判定とどの程度一致し、どのような失敗を見逃すか**を検証することとした。正常な質問だけでは採点器の弱点が見えにくいため、`data/eval/my_cases.jsonl` に質問・期待するふるまいを10件設計した。

コンテキストウィンドウの単位（#01）、LoRAとQLoRA（#02）、ツール呼び出しと構造化出力（#03）、誤前提の訂正（#04）、存在しない第15回の締切（#05）、資料にない人数（#06）、宿題の完成コード要求（#07）、講義外の天気（#08）、架空の出典を指定する指示上書き（#09）、LoRAとツール呼び出しの講義横断比較（#10）を含めた。各質問には、正解の文章ではなく**望ましい応答の条件**を記載した。

### 2. 実験方法

1. 第3回のエージェント（`app.agent`、講義資料を検索するRAG構成）を用い、独自10問への回答を生成した。
2. 回答を、根拠・範囲・ヒント・分かりやすさ・回の表示の5基準で人手判定し、初回のラベルを`lectures/04/my_labels_initial.jsonl`に保存した。
3. `gemini-3.5-flash-lite`（temperature 0、理由を先に生成する構造化出力）で意味に関する4基準を判定した。「回の表示」だけは回答の**最終行**に`第N回`が含まれるか正規表現で判定した。採点結果と理由を`my_judge_result.json`に保存した。
4. ルーブリックと実際の回答を読み直し、初回の人手判定50項目中10項目を修正した。修正後のラベルは`my_labels.jsonl`に保存した。**LLM採点は再実行しておらず、採点器の出力は同じ**である。
5. `scripts/lec04_report.py`で、基準別一致率、判定可能率（coverage）、不合格再現率、見逃し・過検出を算出した。集計表は`my_report.md`に保存した。

### 3. 結果

| 評価基準 | 初回の一致 | 人手確認後の一致 | 人手確認後の不合格再現率 |
|---|---:|---:|---:|
| 根拠 | 10/10 | **9/10** | 0/1 |
| 範囲 | 9/10 | **10/10** | 算出不可（不合格0件） |
| ヒント | 9/10 | **10/10** | 算出不可（不合格0件） |
| 分かりやすさ | 10/10 | **10/10** | 算出不可（不合格0件） |
| 回の表示 | 3/10 | **10/10** | 6/6 |
| **全50判定** | **41/50（82%）** | **49/50（98%）** | — |

採点器が`unsure`を返した項目は**0件**で、判定可能率は**50/50（100%）**だった。必須4基準から算出する総合判定も、人手確認後は**10/10件**一致した。ただし、これは**人手ラベルとの一致率**であり、エージェントの正答率や採点器の真の正確性ではない。総合判定では複数の基準の不合格が同じ総合不合格にまとまるため、基準別の不一致が見えなくなる。

### 4. 不一致事例の考察

**#10：LoRAの説明に含まれる曖昧な表現。** 回答には「モデルの重み自体を直接調整」とあり、続いて「元の重みは固定したまま、低ランク行列を学習」と説明されていた。元の基盤重みを更新すると読める表現を重く見て人手では`grounding=fail`としたが、採点器は後者の正しい説明を重視して`pass`とした。これが修正後に残った**唯一の不一致**である。前者を「追加パラメータの重み」と解釈する余地もあるため、採点器の誤りと断定せず、**「重み」という語の指す対象をルーブリックで区別する必要**があると考えた。

**#05：形式的な合格と出典の妥当性のずれ。** 回答の最終行で存在しない「第15回」に言及すると、正規表現は`第N回`を検出して合格にする。しかし、これは正しい出典を示したことを意味しない。**形式条件を完全に満たすことと、必要な根拠を正しく引用することは別**だと分かった。

**#08・#09：適切な拒否と出典形式の衝突。** 天気の回答や偽の出典を要求された際に、エージェントは適切に応答を控えた。一方、最終行に講義回がなければ「回の表示」は不合格となる。この評価は現在の字句条件には忠実だが、拒否応答の品質評価としては不要な失点の可能性がある。

### 5. コード判定とLLM判定の使い分け

**コードで判定するのが適切なもの**は、完全に定義できる形式条件である。例えばJSONのパース可否、必要なキー・型、`第N回`の字句の有無、引用したページ番号が資料のページ範囲内か、などはプログラムで検証でき、同じ入力に対して同じ結果を再現しやすい。

**LLMで判定する意義があるもの**は、質問への応答の適切さ、誤前提の訂正、説明の明瞭さ、概念の整合性、ヒントに留めているかなど、文脈を考慮する必要がある基準である。ただし、LLMも用語の曖昧さを見逃すことがあるため、理由・判定・`unsure`を記録し、人手で監査する必要がある。

出典の**形式**はコードで検証できても、出典が主張を**裏付けるか**は別の照合が必要である。とくに今回、評価対象のエージェントは講義PDFを検索するのに対し、「根拠」の採点ルーブリックは用語集を基準にしている。この**構成概念妥当性のずれ**により、高い一致率だけで資料への忠実性を主張できない。

### 6. 妥当性・再現性の限界と改善案

- **ラベル修正時のバイアス**：Geminiの採点結果を知った後、対話によって人手ラベルを見直した。82%から98%への増加は採点器自体の改善ではなく、**評価基準の再解釈による一致度の変化**であり、後知恵や確認バイアスの影響を受け得る。独立した評価者による盲検ラベル付けが望ましい。
- **小規模・不均衡なデータ**：10問では推定の不確実性が大きい。修正後の「範囲」「ヒント」「分かりやすさ」は人手で不合格とした例が0件のため、不合格検出能力は測定できない。`unsure=0`も判定の正しさを意味しない。
- **評価基準の改善**：「回の表示」を字句検査と出典の妥当性検査に分離し、講義範囲外の拒否応答に引用を必須とするかを明文化する。LoRAの例では「基盤重み」と「追加アダプタの重み」を区別してルーブリックに書く。
- **今後の検証**：修正した基準を**新しい問題**で評価する、2人以上のラベルを比較する、資料本文・引用ページの照合を追加する、といった方法で一般化可能性と妥当性を高められる。今回は追加実験の結果を主張しない。

### 7. 提出物と再現手順

- 評価ケースと生成回答：`data/eval/my_cases.jsonl`
- 初回・レビュー後の人手判定：`lectures/04/my_labels_initial.jsonl`、`lectures/04/my_labels.jsonl`
- 元のGemini判定とレビュー後の再集計：`lectures/04/my_judge_result.json`
- 詳細な集計表：`lectures/04/my_report.md`
- 解析スクリプト：`scripts/lec04_report.py`、テスト：`tests/test_lec04_report.py`

既存の回答を再生成せず、保存済みの採点結果から現在の人手ラベルを再集計するコマンドは以下のとおり。**実モデルを再採点したい場合のみ**APIキーが必要となる。

```powershell
uv run python -m scripts.lec04_report
uv run pytest -q
```
